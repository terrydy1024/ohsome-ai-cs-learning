# Day 11｜多国家、多语言与规则版本治理方案

## 1. 核心问题

多语言不是把同一答案翻译七次。真正风险是：
- 新加坡会员召回马来西亚规则；
- 中文译文已更新，泰语仍是旧版；
- 未来规则提前进入索引；
- 已失效规则仍因语义相似被召回；
- 内部客服 SOP 被会员端检索到。

所以查询顺序必须是：先确定权限和适用范围，再在合格知识集合内做语义召回。

## 2. 规范事实与译文

每条规则建立一个 `rule_master_id` 和规范语言版本。其他语言不是独立规则，而是绑定规范版本的受控译文，必须记录：
- canonical rule/version；
- 译文语言和翻译版本；
- 本地审核人；
- 审核状态；
- 生效时间；
- checksum。

规范事实变化后，所有受影响译文进入待复核状态，不能继续静默使用旧译文。

## 3. 查询时的硬过滤

1. `security_scope`：会员端不能召回内部知识；
2. `market`：当前市场 + 明确标记 GLOBAL 的通用规则；
3. `business_line` 和 `channel`：避免跨业态、跨渠道误答；
4. `status=published`；
5. `effective_at <= now < expires_at`；
6. 语言优先匹配，缺失时按规则回退规范语言；
7. 在合格集合内进行混合召回和重排。

## 4. 版本状态机

`draft → review → approved → scheduled → published → suspended/retired`

任何时点，同一市场、业务线、渠道和规则主题只能存在一个当前有效版本。发布时检测时间重叠；发现冲突时阻断回答，而不是选择相似度最高的一条。

## 5. 多语言回答策略

推荐顺序：
- 优先使用已审批的用户语言知识；
- 无本地译文但允许回退时，检索规范语言事实，再由模型按术语表生成用户语言答案，并明确引用规范版本；
- 高风险、金额、期限、资格等内容若无审核译文，可转人工，不依赖即时机器翻译；
- 数字、日期、币种和专有名词使用结构化字段，不让翻译模型自由改写。

## 6. 紧急下架与回滚

规则误发或风险事件发生时：
- 将版本标记 `suspended`；
- 查询过滤立即排除；
- 回退上一稳定版本，若不存在则拒答/转人工；
- 查找该版本已影响的会话；
- 修复、回归、重新审批后再发布。
