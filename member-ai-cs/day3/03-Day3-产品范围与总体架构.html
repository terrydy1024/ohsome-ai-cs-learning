产品范围与总体架构

把 Day 2 的 50 个会员咨询场景放进同一套系统：哪些由 API 回答，哪些走 RAG，哪些必须执行受控工作流，哪些应立即转人工。

8 层完整产品架构
25 个逻辑组件
6 种场景路由模式
5 条代表时序流程

一、先看一个典型架构事故

项目组快速上线了一个“接会员 FAQ 的大模型聊天框”。用户问：

“我昨天在门店消费了，为什么积分没到账？”

机器人只检索到“消费后可获得积分”的通用规则，于是回答：“积分通常会在消费后自动到账，请稍后再查看。”

遗漏事实没有查订单与积分流水

无法判断订单是否完成、是否退款、商品是否计积分，以及积分是否已经发放。

错误能力把异常诊断当成 FAQ

RAG 只能提供规则依据，不能替代业务数据查询和多步判断。

缺少失败分支没有数据冲突与转人工

接口异常、超过正常时限或数据冲突时，系统应创建工单或转人工。

无法追责没有工具与知识追踪

出错后不知道是意图识别、接口、规则版本还是答案生成的问题。

二、核心架构结论

推荐形态：受控工作流优先 + 大模型有限决策 + 只读工具调用 + 高风险人工接管。

会员客服不适合在 MVP 阶段使用全自治 Agent。模型可以识别问题、提取参数和组织答案，但不能自由决定是否修改积分、补发优惠券或承诺赔偿。

模型负责

语言理解、场景识别、槽位抽取、追问生成、基于证据表达。

系统负责

鉴权、权限、工具调用、国家隔离、固定流程、错误码与审计。

人工负责

赔偿、隐私、账号合并、数据冲突和不可逆处理。

三、五条架构原则

01事实源分离

个人资产来自 API；规则来自有效知识库；模型不是事实源。

02先确定上下文

国家、品牌、语言、业务线和会员身份缺失时，不能直接检索或查询资产。

03确定性优先

高频且规则明确的场景使用固定工作流，模型只做有限判断。

04MVP 只读

可以查询，不自动补积分、补券、合并账号、退款或赔偿。

05失败时收缩能力

接口失败、无证据、规则冲突和低置信度时追问、拒答或转人工。

四、八层总体架构

1. 渠道与入口
App/H5 客服入口页面上下文答案与操作按钮
2. 接入与会话
AI 服务网关鉴权/限流会话ID/trace_id会员上下文解析
3. 会话理解
语言识别意图识别槽位抽取置信度与缺失信息
4. 编排与策略
场景路由受控工作流风险与权限策略重试/降级/转人工
5. 工具与业务数据
会员档案积分优惠券等级/成长值权益订单/购物车活动门店
6. 知识与 RAG
知识治理后台元数据过滤检索与重排证据组装/冲突识别
7. 回答与护栏
答案生成资产事实校验隐私/承诺检查人工转接与工单
8. 监控与评测
工具与知识追踪耗时/错误/成本点踩与人工改写回归测试集回流
最重要的分工：API 给个人事实，RAG 给有效规则，工作流做确定性判断，模型做理解和表达，人工处理高风险与不可逆动作。

五、六种场景路由模式

T1API 直查

积分余额、当前等级。必须鉴权，接口失败不得生成。

T2RAG 规则解释

积分有效期、升级规则。必须按国家与生效时间过滤。

T3API + RAG 混合

具体券使用规则、个人过期积分。资产与规则分别取事实源。

T4工作流诊断

积分未到账、券不可用。固定步骤、多工具、异常分支。

T5人工优先

赔偿、隐私、账号合并。AI只识别并收集必要信息。

T6导航与信息收集

找入口或信息不足。先追问或展示选择器，不猜答案。

快速判断表

判断问题处理方向
是否在问“我的当前资产/状态”？鉴权后调用业务 API
是否只问通用规则？按上下文过滤后走 RAG
是否同时包含个人事实和规则？API + RAG 混合
是否需要多个系统共同判断原因？受控工作流
是否涉及隐私、赔偿、争议或不可逆操作？人工优先

六、三个代表流程

流程 A：积分余额查询

校验登录态和 member_id，未登录时引导登录。
识别为 PTS-01，选择 T1 API 直查。
调用积分工具，返回余额、冻结和过期批次。
按结构化模板生成答案并标注查询时间。
接口失败时停止输出资产数字，提示重试或转人工。

流程 B：积分未到账

识别场景并提取消费时间、门店和订单。
查询订单是否完成、是否退款、商品是否计积分。
查询积分流水和发放状态。
检索当前国家积分发放时效与排除规则。
工作流判断正常等待、不计积分、已发放、系统失败或数据冲突。
给出原因和下一步；超过时限或冲突时创建工单，不承诺补积分。

流程 C：赔偿或资产争议

识别赔偿、盗用、隐私或强烈投诉等风险信号。
选择 T5 人工优先，不进入自动裁决。
同步会员信息、用户原话、已查数据、证据和转接原因。
记录人工最终结论，回流场景库与测试集。

七、MVP 范围与能力边界

纳入
  • 积分、券、等级、成长值和权益只读查询
  • 当前有效会员规则解释
  • 积分未到账、券不可用等受控诊断
  • 追问、页面导航、工单和人工转接
  • 全链路日志与基础评测
不纳入
  • 自动补积分、补券或延长有效期
  • 账号合并与关键资料修改
  • 自动退款、赔偿和投诉裁决
  • 任意工具自由调用的全自治 Agent
  • 跨会员或无权限数据查询
边界不是保守：第一阶段先把高频、可标准化、可审计的服务做好，再根据真实数据决定是否扩展写操作。直接开放高风险动作会让项目难以通过安全和上线评审。

九、练习与验收

练习 1：为什么不用全自治 Agent

请从权限、可解释、失败恢复和业务风险四个角度说明。

查看参考答案

全自治 Agent 可以灵活规划，但会员客服涉及账户身份、积分、券、等级和权益。自由调用工具会增加越权、参数错误、重复调用、成本失控和无法稳定回归的问题。MVP 应由规则控制登录校验、工具范围、调用顺序和高风险转接；模型只在限定场景中识别、抽取参数和表达答案。这样每一步可以追踪，失败时也能按预定义分支重试、拒答或转人工。

练习 2：如何路由

“我有多少积分”“积分多久过期”“为什么积分没到账”分别走什么路径？

查看参考答案

“我有多少积分”是个人资产，走登录校验和积分 API；“积分多久过期”是通用规则，先确认国家和品牌后走 RAG；“为什么积分没到账”需要订单、积分流水和规则共同判断，走受控工作流。三者不能都归为一个“积分问答”。

练习 3：接口失败

积分接口失败，但 RAG 有积分规则，系统应该怎样回答？

查看参考答案

可以解释通用积分规则，但必须明确当前无法查询个人积分，不得生成余额或断言积分状态。系统可以自动重试一次，仍失败则提示稍后再试或转人工，并记录接口错误和 trace_id。规则回答与个人资产回答要明确分开。

完成检查

十、面试追问与示范回答

追问 1：为什么不是接一个大模型加知识库就可以？

回答重点：知识库只能解释规则，不能提供会员实时资产，也不能完成订单、积分、券和活动之间的异常诊断。完整系统需要会员上下文、意图识别、API 工具、RAG、受控工作流、护栏和人工接管。

追问 2：为什么你们还称它为 Agent？

回答重点：它具备基于意图选择工具、结合工具结果继续决策和执行多步任务的能力，但 Agent 自主权受到策略和工作流约束。我们采用 workflow-first 的受控 Agent，而不是让模型无限制规划。

追问 3：工具结果怎么给大模型？

回答重点：工具适配层把业务接口转换为稳定、最小化、脱敏的结构化对象，只保留当前场景必要字段。模型拿到的是经过权限校验和字段筛选的 facts，不是完整原始响应。

追问 4：规则和接口结果冲突怎么办？

回答重点：先区分冲突类型。个人资产状态以业务 API 为准，规则解释以有效规则版本为准；如果业务结果违反规则预期，则属于异常，需要进入工作流或人工核查，不能让模型自行修改事实或选择更“合理”的结果。

追问 5：如何支持多国家？

回答重点：在检索和工具调用前建立国家、品牌、语言和业务线上下文；RAG 先做元数据硬过滤，再做语义召回。国家和生效时间不交给相似度或模型猜测。跨国规则缺失或冲突时转人工。

Day 3 验收方式

不看稿，用 8 分钟讲清：

  1. 为什么采用受控工作流而不是全自治 Agent；
  2. 完整八层架构及每层责任；
  3. API、RAG、工作流、模型和人工如何分工；
  4. 积分余额、规则解释和积分未到账为什么走不同路径；
  5. MVP 为什么只读，以及接口失败如何降级。
