优惠券、生日礼与权益异常工作流

将三类会员权益异常统一为可查询、可诊断、可解释、可安全接管的受控流程。

本章目录本章任务1. 统一诊断骨架2. 三类事实与规则3. 优惠券原因树4. 生日礼与权益5. 原因码练习与验收面试追问

优惠券、生日礼和会员权益看起来是三类问题，但它们可以共享同一套异常诊断框架：先确认本人对象，再组合状态、资格、轨迹和当前规则。

贯穿事故
用户说“券用不了”。AI只检索到优惠券通用规则，就回复“可能是未满100元”。真实原因却是券已被另一笔未支付订单锁定。用户反复加购仍无法使用，最终投诉。问题不在语言表达，而在AI没有查询券状态和交易轨迹。
本章完成后，你需要做到：
  • 用统一框架拆解券、生日礼和权益异常
  • 设计稳定原因码和工具轨迹
  • 明确可以回答、建工单和转人工的边界
  • 避免自动补券、补礼和恢复权益次数
01

统一异常诊断骨架

定位本人对象券/礼/权益
查询状态事实生效/使用/锁定
判断资格条件市场/渠道/门槛
查询业务轨迹发放/领取/核销
检索当前规则国家/版本/时间
输出原因码稳定结论
回答或接管解释/工单/人工
02

三类问题分别查什么

场景需要的个人事实需要的规则不能做
优惠券不可用券状态、有效期、使用/锁定记录、交易资格结果渠道、门店、商品、门槛、叠加、市场模型自行计算门槛或补券
生日礼未发生日资料状态、会员资格、发放/领取记录活动周期、资格条件、发放SLA回显完整生日或承诺补发
权益核销失败权益状态、剩余次数、核销轨迹适用门店/渠道、核销条件、重试规则恢复次数或绕过核销
03

优惠券不可用原因树

券属于当前会员？ ├─ 否/无法证明 → CPN_NOT_OWNED → 不披露 + 转人工 └─ 是 ├─ 未生效 / 已过期 / 已使用 / 被锁定 → 直接解释状态 └─ 状态有效 ├─ 渠道 / 门店 / 商品 / 币种不符 → 资格原因码 ├─ 门槛不足 / 叠加冲突 → 说明具体条件 └─ 工具与规则均显示可用但仍失败 → 建工单
04

生日礼与权益的关键边界

生日礼

模型只需要知道生日资料是否完整，不需要完整生日。符合资格且超过SLA也只能创建核查工单。

权益核销

先确认是否已有成功记录，防止重复核销。只有错误码明确允许且没有成功记录时才指导重试。

05

代表性原因码

原因码含义系统动作
CPN_THRESHOLD_NOT_MET符合条件金额未达到门槛展示工具返回的金额、门槛和差额
CPN_NOT_OWNED无法证明券属于当前账号不披露详情，转人工
GIFT_ISSUE_OVER_SLA资格通过但超过发放时限创建幂等核查工单，不承诺补发
BENEFIT_ALREADY_REDEEMED已存在成功核销记录阻止重复操作，争议转人工
RULE_VERSION_CONFLICT当前有效规则互相冲突停止确定回答并记录治理事件

练习与验收

问题1

用户的优惠券显示有效，但结算页不能用。你会按什么顺序查询？

问题2

生日礼超过发放时间，为什么仍不能自动补发？

问题3

权益核销接口返回失败，但随后查询到成功记录，系统应如何处理？

参考答案
先确认本人券和生命周期，再调用资格判断检查渠道、门店、商品、金额、叠加和币种，最后结合当前规则解释；超过SLA只是异常信号，仍需核查资格、发放轨迹和系统冲突，AI没有补偿权限；查到成功记录后禁止再次核销，向用户说明状态并在有争议时创建工单。
答

面试追问

优惠券门槛为什么不能让模型自己算？
可计入门槛的金额可能需要排除特定商品、折扣、税费、退款和渠道，必须由业务资格工具按统一口径计算。模型只展示工具结果。
三个异常场景为什么要统一原因码？
不是共用完全相同的原因码，而是共用原因结果结构。这样工作流、回答、人工接管、评测和线上监控可以按同一种契约消费。
