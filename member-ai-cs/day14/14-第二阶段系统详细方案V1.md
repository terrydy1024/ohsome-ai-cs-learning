# OH!SOME 多国家会员 AI 客服｜第二阶段系统详细方案 V1

## 1. 当前方案结论

第二阶段采用“单入口服务 Agent + 代码策略与状态机 + Tool Gateway + 会员只读 API + 会员规则 RAG + 确定性异常原因树 + 回答护栏 + 人工接管”的总体方案。

模型负责语言理解、槽位抽取、候选工具建议和自然语言表达；代码负责路由、参数校验、状态、重试、原因判断和高风险停止条件；业务系统负责个人资产、资格和交易事实；知识库负责当前有效规则；人工负责补偿、投诉、账号安全和复杂争议。

## 2. 为什么不是“一个大模型接知识库”

会员客服包含四种本质不同的问题：个人资产查询、规则解释、异常诊断和高风险处置。RAG只能提供规则证据，不能确认个人积分、券、订单和权益状态；异常诊断还需多工具调用和确定性原因树；投诉和赔偿需要人工权限。

## 3. 为什么一期不采用多 Agent

一期场景共享同一会员身份、会话上下文、工具和知识库。拆成多个Agent会增加路由、上下文传递、跨Agent错误归因和评测成本，尚无明确收益。因此保留单入口 Agent，在代码层按路由模式调用固定RAG、单工具、混合流程、受控状态机或人工接管。

## 4. 核心组件

1. App/H5入口与会话上下文。
2. 分层意图和槽位识别。
3. 策略路由、状态机、超时重试和人工分流。
4. 身份认证、对象归属、工具scope、字段最小化和审计。
5. Tool Gateway：严格Schema、参数校验、统一响应和稳定错误码。
6. 会员业务系统：账户、订单、积分、优惠券、权益事实。
7. RAG：知识采集、切片、元数据过滤、召回、重排、引用和版本治理。
8. 异常原因树：积分、优惠券、生日礼和权益异常。
9. 回答和护栏。
10. 人工接管、评测和线上监控。

## 5. 核心接口契约

- intent_result：业务域、动作、场景ID、槽位、风险标记和置信度。
- authorization_result：身份等级、对象归属、scope、允许字段和审计ID。
- tool_result：状态、最小数据、稳定错误码、是否可重试和数据时间。
- evidence_bundle：证据片段、规则版本、来源、生效范围和冲突标记。
- diagnosis_result：原因码、支持事实、证据ID和下一步动作。
- handoff_package：最小会员上下文、用户问题、工具轨迹、证据、原因码和AI已回复。

## 6. 关键方案决策

- 简单规则问答走固定RAG，不必进入自由Agent规划。
- 会员内部API不直接暴露给模型，必须经Tool Gateway包装。
- 会员资产工具只读；补积分、补券、退款和账号合并不进入工具箱。
- 规则版本按市场、语言、渠道、状态和生效时间硬过滤。
- 关键异常原因由代码原因树判断，模型不能覆盖确定性结论。
- 超过SLA只表示需要核查，不代表AI可以自动补偿。
- 无有效证据、规则冲突和对象归属失败时停止确定回答。

## 7. 非功能与审计要求

每次会话应产生trace_id，记录意图结果、授权、工具请求与响应、知识证据、原因码、输出护栏结果和人工接管。敏感字段按最小化原则进入上下文，并按生命周期清理。

响应时间需按路由分层统计：纯规则问答、单工具查询和多工具诊断不能只报一个平均值。最终门槛需通过真实流量基线和灰度验证。
