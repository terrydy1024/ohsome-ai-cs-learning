线上监控与故障排查

建立业务质量、安全、性能、成本和人工协同指标，并用全链路Trace完成故障定位。

本章目录本章任务1. 解决率口径2. 指标体系3. Trace4. 告警5. 排障顺序6. 反馈回灌练习与验收面试追问

上线后的关键不是“看一个大盘”，而是知道用户是否真的解决、哪里开始异常、哪个版本造成回退，以及怎样在分钟级止损。

贯穿事故
某周自助解决率持续上升，团队认为效果更好；但投诉和24小时复联同时上升。检查后发现“没有转人工”被错误地当成“已解决”，大量错误回答和用户放弃被计入成功。
本章完成后，你需要做到：
  • 定义自助解决率、转人工率和质量指标的正确口径
  • 建立按市场、语言、场景和版本拆分的监控
  • 用trace定位工具、RAG、生成和人工问题
  • 设计告警、自动动作、Runbook和反馈回灌
数据说明
本章看板和阈值为学习模拟，重点是指标口径和排障方法。
01

不要把“没转人工”当解决

自助解决率建议口径
无转人工、无24小时同问题复联、无负反馈，并且任务完成的会话 ÷ AI合格会话。

分母还要排除测试、闲聊、广告、重复请求和未开放场景。否则不同团队会得到完全不同的“75%”。

02

六类线上指标

业务

合格会话、解决、转人工、复联。

质量

资产、规则、证据、追问和分流。

安全

P0、越权、承诺和攻击。

体验

首字、完整P95、负反馈和中断。

稳定与成本

可用性、错误、Trace和单解决成本。

运营

知识缺口、人工SLA和问题入集。

03

关键会话必须可追踪

trace_id ├─ 市场 / 语言 / 意图 / 会话状态 ├─ 身份 / 对象归属 / 权限结果 ├─ 模型 / Prompt / 工作流版本 ├─ 工具 / 参数摘要 / Schema / API结果 ├─ RAG过滤 / TopK / 文档 / 知识快照 ├─ 输出护栏 / 最终动作 / 转人工原因 └─ 分段耗时 / Token / 成本 / 用户反馈

没有这些证据，出现误答时只能靠猜，最终所有问题都会被错误归因到“模型不稳定”。

练习与验收

问题1

为什么“未转人工会话 / 全部AI会话”不是可靠的自助解决率？

问题2

AI返回错误国家规则时，最少要查看哪些trace字段？

问题3

自助率提升但投诉上升，你会先检查什么？

参考答案
未转人工可能是用户放弃或AI错误强答；需查市场上下文、检索过滤、知识元数据、版本、TopK和最终引用；先核对解决率口径，再按场景和版本抽样，检查漏转、错误回答和用户复联。
答

面试追问

转人工率越低越好吗？
不是。要结合正确转人工率、自助解决率、复联、投诉和高风险漏转一起看。
如何证明75%真的解决了？
需要明确分母、任务完成信号、24小时复联、负反馈、人工接管和观察期，并按场景分层。
线上错误为什么不能只看最终答案？
最终答案可能由错误API、错误知识、检索串库、生成不忠实或护栏改写导致，必须查看全链路trace。
